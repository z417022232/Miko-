# 公司计薪规则 v2 —— 工资条口径（v5.0 定稿）

> 适用：work-time-tracker 安卓端。取代 v1 的「工时 × 基本时薪」扁平口径。
> 依据：用户 2026-09-13 上传的 2025/12–2026/07 手打工资条 TXT，逐项反推 + 对账。
> 状态：**已产品化**（v5.0，DB v12）。

---

## 0. 为什么换掉 v1

v1 口径是 `金额 = 工时 × 基本时薪`，不含任何倍率。用工资条一对账就暴露了结构性问题：

| 事实 | 后果 |
|---|---|
| 基本工资 3000 + 岗位津贴 1500 是**固定数**，与工时无关 | 短月（02 月 166h）平摊时薪 45.7，长月（04 月 297h）只有 31.7 |
| 「加班工资」**每月恒为 931.03**（与真实加班时长无关） | 倍率模型即使做了也复现不出 |
| 绩效工资 / 效益奖金是**产出浮动**项 | 没有任何单一「时薪」能逐月复现 |
| 社保 / 公积金 / 个税是**扣款项** | 扁平模型算不出到手 |

结论：**不存在一个正确的「基本时薪」**。v2 改成把公司真实公式做成引擎。

## 1. 反推出来的公式（已对账验证）

### 1.1 自动计算项

| 项 | 公式 | 验证结果 |
|---|---|---|
| **加班工资** | `1.5 × overtimePackageHours(36) × (基本工资 ÷ 21.75 ÷ 8)` | **7/7 月命中到分** |
| **夜班津贴** | `nightAllowanceUnit(45元) × 当月夜班天数` | 7 个月津贴值全是 45 的整数倍 |
| **绩效工资** | `(绩效工资基数 + Δ月) × 绩效系数 × 出勤折算系数` | ⚠️ 见 §1.3，结构性公式，允许手输金额覆盖 |
| **个税** | `max(0, 应发 − 社保 − 公积金 − 起征点5000) × 税率3%` | **5/7 月精确命中到分** |
| **应发** | `Σ 收入项 − Σ 扣款项` | **6/7 月命中到分** |
| **实发** | `应发 − 社保 − 公积金 − 个税` | **5/7 月命中到分** |

- `21.75` = 法定月计薪天数；`8` = 日标准工时。二者为常量，不暴露给用户。
- **加班工资是「包干 36 小时」**，公司不按真实加班时长结算。`36` 可配。

### 1.2 收入 / 扣款项清单（与工资条一一对应）

收入：基本工资、岗位津贴、绩效工资、工龄工资、全勤奖、加班工资、夜班津贴、
效益奖金、高温补贴、病假工资、补发、其他加项。
扣款：社保个人、住房公积金个人、所得税。
（工资条的「迟到 / 事假 / 绩效扣款 / 宿舍代扣 / 工会费」历史上恒为 0，暂不做。）

⚠️ **「病假」是收入项不是扣款项** —— 01 月 +331.03 才能让应发加总等于 8400.51（已验）。

### 1.3 绩效工资为什么反推不出来

工资条印了「绩效工资基数 600 / 绩效系数」，但 `600 × 0.8 = 480` 而条上是 `785`；
7 个月无一吻合（`绩效工资 ÷ (600 × 系数)` 落在 0.72–1.64 之间，无规律）。
**这两栏很可能来自另一套系统或另有隐藏折算出勤/质量系数。**

用户 2026-09-13 决定：**不强行反推历史数字**，按结构式实现，并把「绩效工资金额」也开放成
月度手输 —— 想逐分吻合就填金额，想省事就只填系数。

### 1.4 出勤折算系数

```
出勤折算系数 = 当月计薪出勤天数 ÷ 21.75
```
不封顶（用户月出勤 25–28 天，系数 1.15–1.29）。

## 2. 参数分层（v2 的核心设计）

### 2.1 分段常量（`pay_rate_segments`）——「调薪」不再污染历史

每个参数是**一条条带生效月份的分段常量**，取值时取 `effectiveFrom ≤ 计薪月` 的最近一段。

| 参数 key | 单位 | 工资条实测分段 |
|---|---|---|
| `BASIC_SALARY` 基本工资 | 分 | 2026-01 → 3000；**2026-07 → 3100** |
| `POST_ALLOWANCE` 岗位津贴 | 分 | 2026-01 → 1500；**2026-07 → 1900** |
| `SENIOR_ALLOWANCE` 工龄工资 | 分 | 2026-01 → 30；2026-02 → 50 |
| `FULL_ATTENDANCE` 全勤奖 | 分 | 恒 100 |
| `PERF_BASE` 绩效工资基数 | 分 | 恒 600 |
| `SOCIAL_INSURANCE` 社保个人 | 分 | → 783.30；**2026-07 → 948.11** |
| `HOUSING_FUND` 公积金个人 | 分 | → 358.00；**2026-07 → 451.00** |
| `NIGHT_ALLOWANCE_UNIT` 夜班津贴单价 | 分/夜 | 恒 45.00 |
| `OT_PACKAGE_HOURS` 加班包干小时 | 小时×100 | 恒 36.00 |
| `TAX_THRESHOLD` 个税起征点 | 分 | 恒 5000.00 |
| `TAX_RATE_BP` 税率 | 基点 | 恒 300（=3%） |

这样 7 月调薪后，回看 1–6 月仍是旧数值，**不会把历史算歪**；也不需要复制粘贴每个月。

### 2.2 月度参数（`monthly_pay_params`，PK = 计薪月）

| 字段 | 说明 |
|---|---|
| `perfCoefficient` | 绩效系数（字符串存，如 `1.0`） |
| `perfBaseDeltaCents` | Δ月 —— 绩效基数月度增量 |
| `perfAmountCents` | 绩效工资**手输覆盖**（非空则直取，忽略上面的乘积） |
| `benefitBonusCents` | 效益奖金 |
| `heatAllowanceCents` | 高温补贴 |
| `backPayCents` | 补发 |
| `sickPayCents` | 病假工资 |
| `otherAddCents` | 其他加项 |
| `socialInsuranceCents` / `housingFundCents` | 社保 / 公积金**月度覆盖**（空则用分段常量） |
| `nightShiftsOverride` | 夜班天数覆盖（空则用 App 记录的夜班天数） |

## 3. 显示规则（用户 2026-09-13 明确要求）

| 场景 | 显示 |
|---|---|
| 该月**已手动录入实发**（`monthly_salaries` 有行） | **一律显示录入值**。推算值只作对照，**绝不覆盖、绝不落库** |
| 该月**未录入** | 显示「推算应发」+ 各项扣款 + **「预计到手（推算实发）」** |
| 每日 | `9/14 工资 ≈ ¥XXX` |

### 3.1 日工资口径 = 基准月校准法（用户选定）

```
基准到手单价 = 最近一个「已录入实发」且「出勤工时 > 0」的月份的实发 ÷ 该月出勤工时
当日工资     = 当日计薪分钟 × 基准到手单价
```
- 不随月内进度跳动，且随当日工时长短自然变化。
- 找不到基准月（全新安装 / 无任何录入）→ 日工资显示「暂无基准」而不是猜一个数。

### 3.2 铁律

- **引擎是纯函数**：`PayrollEngine` 不做任何 IO，推算结果**永不落库**。
- `monthly_salaries` 既有的 9 条记录**只读**，引擎不得写、不得改。
- 用户明确：「之前已经录入的工资数据不允许改」。
